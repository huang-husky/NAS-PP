Motivation: what does an LLM encoding really contribute?
2
•  Recent work writes architectures as text or code and uses language models to predict performance (e.g., Akhauri et al., ICML 2026)
•  Architecture encoding strongly affects performance predictors (White et al., NeurIPS 2020; 2021), but what LLM-based encodings actually encode has not been tested
•  Existing work compares different LLM backbones (e.g., CodeLlama vs. Llama, model sizes), but rarely includes two controls: (a) the same LLM without pretraining (random init), and (b) token counts of the text, with no LLM at all
Two questions
①  Do frozen LLM features encode the full architecture (which op sits on which edge), or only a coarse summary (how many times each op is used)?
②  How much does pretrained knowledge help? (Same LLM: pretrained vs. random init; plus comparison with non-LLM encodings such as one-hot)

Setup: how features are built and how predictors are evaluated
3
Pipeline: architecture → PyTorch-style code → frozen LLM → mean of last-layer outputs = feature vector
Evaluation
1.  Sample n labeled architectures (n = 10–2000) and train a regressor (ridge / random forest / MLP) on their features
2.  Predict all remaining architectures in the search space
3.  Kendall τ between predicted and true ranking (1 = perfect); N@10 = true rank of the best architecture among the top-10 predicted
4.  20 random seeds; same pipeline with non-LLM features (one-hot, op counts, token counts) as controls
Search spaces
NAS-Bench-201 (all 15,625); TransNAS-Bench-101 micro (all 4,096, 7 tasks); NAS-Bench-101 (5,000 random)
LLMs
Pythia 70M / 160M / 410M / 1B, each at random init and fully trained; Qwen2.5-0.5B; all frozen
Controls
one-hot (hand-crafted); op counts (5 numbers); token counts of the code (bag of words)
Statistics
Paired Wilcoxon test over seeds (same training splits)

PAGE 5
Explanation: LLM features ≈ token counts of the code
5
Where the ceiling comes from: by "how many times each op is used", the 15,625 architectures fall into only 210 groups; even knowing each group's true mean accuracy, τ is at most 0.629
①  Counts are enough
Just 5 op counts reproduce the LLM's small-sample advantage, and do even better
②  Position barely matters
Randomly moving ops to other edges barely changes LLM features with few samples
③  Probing
75% of the variance in random-Pythia features is linearly explained by op counts
④  Direct comparison
Token counts of the code give learning curves almost identical to the LLM features
Pretraining gives no consistent benefit: the randomly initialized model is often the best (exceptions: TransNAS and the MLP head with many samples)
NOTES: Where the ceiling comes from: counting how often each op is used splits the 15,625 architectures into only 210 groups that cannot be separated, so τ is at most 0.629. All four pieces of evidence say LLM features are basically token counts. A side result: pretraining gives no consistent benefit.

Rule 2: the text format, not the model, sets the ceiling
6
•  The same architecture in 5 formats: code, edge list, sorted ops, natural language, posword
•  Correlation between LLM τ and the format's token-count τ: random Pythia 0.93, trained 0.88, Qwen 0.86
•  The mean gap is only about 0.04
•  Only posword (one dedicated word per "position + op") has no ceiling
An LLM cannot create information that is not in the text: to raise the ceiling, change the format, not the model
NOTES: The same architecture written in 5 formats. Each point is one format, space, task and sample size; the x-axis is the token-count score of that format, the y-axis the LLM score. Points lie on the diagonal: whatever the LLM achieves, token counts achieve too. Only posword, with one word per position and op, has no ceiling.

So 0.797 does not come from the format; most likely it comes from the regression head, which still needs checking.

PAGE 10
Summary
10
Mean-pooled frozen LLM features ≈ token counts of the code
This explains three phenomena at once:
Better than one-hot with few samples: token counts split architectures into a few groups, which are easy to learn
Capped with many samples: architectures in the same group cannot be told apart
No consistent gain from pretraining: token counts leave no room for pretrained knowledge
Holds across 3 search spaces · 5 formats · Pythia 70M–1B · Qwen2.5-0.5B; in search it is even an advantage
NOTES: In one sentence: mean-pooled frozen LLM features are basically token counts of the code. This explains three phenomena at once and holds across three spaces, five formats, and models of different sizes and families.

Limitations: so far only "evaluate → find patterns"
11
Following the route of Ji et al., Loss Functions for Predictor-Based NAS (ICCV 2025): evaluate under a unified setting → find patterns → propose a method based on them
No method yet
We found and explained the problem, but have not yet proposed a new predictor based on it
Limited scale
The largest model is only 1B; only 3 tabular benchmarks, no larger space such as DARTS
No comparison with specialized predictors
Not yet compared with GNN, CAP, DAP or other dedicated predictors
NOTES: Following the route of Ji et al.'s Loss Functions for Predictor-Based NAS: unified evaluation, find patterns, then propose a method. We have done the first two steps. Three things are missing: a method, scale, and a comparison with specialized predictors.
